# OpsMind 三轮优化前后在线评测对比

## 1. 对比口径

| 轮次 | 原始报告 | 说明 |
|---|---|---|
| 初始基线 | `online_eval_20261102_123652.md` | 完成 OpsMind 场景改造后的首轮真实在线评测 |
| 第一轮优化 | `online_eval_20261102_142814.md` | 重点优化意图分类边界，首次结构化人工交接与澄清 |
| 第二轮优化 | `online_eval_20261102_150511.json` | 重点优化对话完整性、人工交接动作与服务目录知识 |

三轮均采用：

- 相同模型：`deepseek-flash`
- 相同意图数据：133 条用例，覆盖 19 类意图
- 相同对话数据：14 组、28 轮对话
- 相同 Judge 规则与 0.75 通过阈值
- 未修改评测标注、未删除难例、未针对单条用例硬编码预测结果
- 三次 Judge 降级率均为 0，没有使用 0.5 兜底分掩盖解析失败

知识库在前两轮均为 6 篇演示文档；第二轮优化有意新增 1 篇服务目录，第三轮为 7 篇。这是本轮优化变量之一，不能把第三轮提升全部归因于 Prompt 或 token 调整。

## 2. 初始指标不佳的原因

### 2.1 意图 Prompt 过度强调细粒度分类

初始 Prompt 要求“能匹配细粒度业务意图时优先返回细粒度意图”，但没有说明选择细粒度标签所需的最低证据。这导致模型面对一般故障描述时，也倾向于猜测 `service_outage`、`application_error` 或 `performance_issue`，而不是保留为通用 `incident`。

账号资料、绑定信息、员工目录和生命周期管理等通用 `access` 请求，也容易被误判为 `change_request` 或 `permission_request`。初始轮次中，`incident` 和 `access` 的 F1 均为 0。

### 2.2 相邻业务流程之间缺少明确边界

初始 Prompt 没有充分区分：

- 普通功能不可用与明确报错、性能下降、大面积中断；
- 账号资料维护与生产配置变更；
- 工单字段维护、催办与变更申请、人工升级；
- 变更/权限流程中的页面异常与主要诉求为应用故障。

初始 133 条意图用例共误判 22 条，Macro-F1 为 0.7975。

### 2.3 人工升级节点回复过于模板化

初始人工升级节点只返回意图、紧急度和实体 JSON，再附加一句安全提醒，没有整理用户原始诉求、最近对话、待补字段和具体后续动作。初始 7 个未通过对话中，有 5 个来自该节点，主要表现为完整性和有用性不足。

### 2.4 澄清引导与知识覆盖不足

低置信度场景只有笼统追问，没有清楚列出用户应补充的信息结构。服务台办公时间和咨询渠道等知识型问题缺少对应服务目录条目；系统为避免虚构答案只能说明无法确认，因此即使回答安全、准确，完整性得分仍然偏低。

## 3. 第一轮优化：解决意图边界和固定短回复

### 3.1 优化措施

1. 增加细粒度证据门槛：只有出现明确错误、性能、影响范围或安全证据时才选择细粒度意图；证据不足时返回对应通用意图。
2. 补充相邻类别判定规则，明确一般故障、账号访问、权限申请、工单流程和生产变更之间的边界。
3. 按主要诉求分类：变更发布或权限流程中伴随页面异常时，优先识别主要业务流程；单纯催办不再直接视为人工升级。
4. 将人工升级改为结构化摘要，加入用户诉求、最近请求、优先级、非空实体、待补字段和系统操作边界。
5. 将低置信度澄清拆为服务对象、具体现象/诉求、期望处理方式三项。
6. 保持评测标注、三路融合权重和数据划分不变；第一轮代码回归测试 16/16 通过。

### 3.2 第一轮结果与未解决问题

意图准确率从 83.46% 提升至 93.98%，错误数从 22 条降至 8 条，说明分类边界优化有效。

但对话通过数仍为 21/28，完整性和有用性没有整体提升。进一步分析发现：

- 普通 Agent 输出预算只有 900～1200 tokens，部分长回复在列举途中结束；
- 通用回复契约没有稳定要求“直接答案、依据、下一步和边界”同时出现；
- 人工交接虽然结构化，但安全事件缺少立即可执行的安全建议，人工等待场景没有说明系统已完成什么、人工接手后做什么；
- 服务目录仍未覆盖办公时间和咨询渠道。

这些问题成为第二轮优化的直接依据。

## 4. 第二轮优化：提升对话完整性与可执行性

### 4.1 优化措施

1. **减少回复截断**：普通 Agent 默认输出上限提高到 2048 tokens，服务台为 1600，事件 Agent 为 2000，多 Agent Composer 为 2000。
2. **统一回复完整性契约**：要求先直接回应核心问题，再给出已知依据和具体下一步；只在必要时询问缺失字段，不能只以反问代替帮助；知识未覆盖时给出可靠核验渠道。
3. **完善安全事件交接**：增加可信设备、官方自助改密、终止其他会话、保留异常时间/IP/设备/下载记录等安全建议，同时明确系统未执行封禁、断网或威胁清除。
4. **完善故障和人工等待交接**：明确当前系统已经完成意图识别、诉求归并、实体整理和摘要生成；说明人工接手后如何继续处理，避免要求用户重复描述。
5. **动态生成待补字段**：已提供的账号、服务或日期不再机械重复追问；缺少的信息按场景生成。
6. **补充服务目录知识**：新增明确标注为演示配置的办公时间和咨询渠道，工作日 09:00-18:00、自助能力全天可用；不编造真实门户 URL、邮箱或服务承诺。
7. 第二轮代码回归测试 17/17 通过，新增安全交接测试，并在评测前验证服务目录能够被 RAG 检索命中。

## 6. 重点意图类别变化

| 意图类别 | 初始 F1 | 第一轮 F1 | 第二轮 F1 |
|---|---:|---:|---:|
| `access` | 0 | **0.9231** | 0.8000 |
| `incident` | 0 | **0.9333** | 0.8235 |
| `application_error` | 0.6000 | 1.0000 | 1.0000 |
| `change_request` | 0.5714 | 0.8333 | **0.9231** |
| `request` | 0.6000 | 0.8571 | 0.8571 |

初始最低类别 F1 为 0；第二轮最低类别 F1 为 0.8000。第一轮针对分类边界的改进在第二轮没有继续修改意图 Prompt，因此第二轮 2.25 个百分点的准确率波动应视为需要持续观察的在线模型波动，不能隐藏，也不应仅凭单次结果回滚已验证的优化。

## 7. 对话优化效果与剩余问题

第二轮改善的典型用例：

- `dialog_7_turn_0`：0.725 → **0.8125**，安全事件交接通过；
- `dialog_7_turn_1`：0.600 → **0.7875**，安全处置请求通过；
- `dialog_11_turn_0`：0.625 → **0.900**，长回复不再中途截断；
- `dialog_13_turn_1`：0.7375 → **0.8375**，服务渠道问题能够基于演示知识直接回答。

剩余 3 个失败用例为 `dialog_6_turn_1`、`dialog_12_turn_0` 和 `dialog_12_turn_1`，均集中于负责人或立即人工接管场景。当前演示系统没有接入真实工单、通知或人力调度系统，只能生成交接摘要和外部渠道指引，不能诚实宣称“已接通人工”。后续若要继续提高这类用例，需要真实人工接管集成或更清晰的演示验收标准，不能通过伪造接管结果追分。

## 8. 结论与限制

两轮优化形成了完整的“失败分析 → 通用原因定位 → 代码与知识优化 → 同数据集真实复测”闭环：

- 第一轮主要解决意图识别问题，准确率提升 10.52 个百分点；
- 第二轮主要解决对话完整性、可执行性和知识覆盖问题，对话通过数增加 4 条，综合通过率提升 13.80 个百分点；
- 最终综合通过率为 89.66%，意图准确率为 91.73%，对话通过率为 89.29%。

这些结果来自真实在线调用，而不是离线推算。由于优化依据包含对前轮失败明细的分析，且复测使用同一数据集，本对比适合证明该数据集上的回归改进，不应直接视为独立未见数据上的泛化提升。模型生成和 Judge 评分也存在随机性，第二轮意图指标的小幅下降已保留在报告中。

各轮 OpsMind 评测结果均独立记录，优化过程未修改评测数据集与 Judge 评分口径。
